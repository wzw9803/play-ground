### 7.1.1-Q3 三种异构预测输出如何统一为 per-tile 概率

【答复草稿】

交底书明确给出了融合公式 P_final(tile, t) = w_short(t) * P_kalman(tile, t) + w_medium(t) * P_markov(tile, t) + w_long(t) * P_nn(tile, t)，但未说明三种中间概率的具体计算方法。以下基于交底书描述的各层输出特征，给出自洽的计算方案。

**一、从卡尔曼轨迹点序列到 P_kalman(tile, t)**

卡尔曼滤波器的输出是未来 5 秒内的轨迹点序列 {(x_k, y_k, z_k, t_k)}，每个点带有协方差矩阵（卡尔曼滤波的固有输出）。

【建议方案-待发明人确认】选A
- A. 最近距离法：对给定 tile 和时刻 t，取预测轨迹在时刻 t 的位置点 p(t)，计算 p(t) 到 tile 包围盒（boundingVolume）的最近距离 d。P_kalman(tile, t) = exp(-d^2 / (2*sigma^2))，其中 sigma 为卡尔曼滤波器在 t 时刻的位置估计标准差（从协方差矩阵对角线提取）。物理含义：若瓦片离预测位置越近、预测不确定性越小，则该瓦片被看到的概率越高。该方案充分利用了卡尔曼滤波的概率输出特性；
- B. 视锥体包含法：对时刻 t 的预测位置构造模拟视锥体，若 tile 的包围盒与视锥体相交则 P_kalman = 1.0，否则为 0.0（二值判定）。再用卡尔曼协方差做边缘软化——若 tile 在视锥体边缘附近（距离视锥体边界小于阈值），概率按距离衰减。该方案更贴近实际渲染逻辑，但实现复杂度较高；
- C. 简化的二值法：方案 B 的简化版，不做软化，相交为 1、不相交为 0。实现最简单，但丢失概率信息。

建议选 A，理由：(a) 卡尔曼滤波天然输出高斯分布，方案 A 直接利用该特性；(b) 计算高效（只需点到包围盒距离 + 指数函数）。

**二、从语义区域概率到 P_markov(tile, t)**

马尔可夫链输出各语义区域（如 building/road/open_area）的访问概率分布，而非 per-tile 概率。需要建立从语义区域到具体瓦片的映射。

【建议方案-待发明人确认】选B
- A. 均匀分配法：对于每个语义区域类型 r，找出所有标注为该类型的瓦片集合 Tiles(r)。P_markov(tile, t) = P_markov_region(r, t) / |Tiles(r)|，其中 r = tile 所属语义区域，P_markov_region(r, t) 是马尔可夫链输出的区域 r 在时刻 t 的访问概率。即假设同一语义区域内的瓦片被等概率访问。优点是计算简单，缺点是忽略瓦片空间位置差异；
- B. 空间加权法：在方案 A 基础上，进一步按瓦片与预测未来位置的空间距离加权：P_markov(tile, t) = P_markov_region(r, t) * w_distance(tile, t)，其中 w_distance 为距离衰减因子（如 exp(-d/R)，R 为可视范围）。优点是考虑了同类区域内的空间差异；
- C. 区域中心法：不直接分配 per-tile 概率，而是将马尔可夫输出视为区域级概率，在融合时 P_markov 作为乘性调节因子作用在 P_kalman 的基础上，即 P_markov(tile, t) 不独立计算，而是定义 P_combined = P_kalman * (1 + lambda * P_region_bonus)，其中 P_region_bonus 对高概率区域的瓦片施加正向偏置。

建议选 B（空间加权法），理由：兼顾区域级统计规律和空间位置差异，计算量适中。

**三、从多条候选轨迹到 P_nn(tile, t)**

LSTM/Transformer 输出 k 条候选轨迹（如 beam search 的 top-k 结果），每条轨迹带有概率权重 w_i（由模型输出的 logits 经 softmax 归一化得到），sum_i w_i = 1。

【建议方案-待发明人确认】选A
- A. 轨迹级加权平均法：对每条候选轨迹 i，用与 P_kalman 相同的方法（如最近距离法方案 A）计算该轨迹下 tile 的概率 p_i(tile, t)，然后加权聚合：P_nn(tile, t) = sum_i w_i * p_i(tile, t)。该方案直接复用 P_kalman 的计算管线；
- B. 轨迹集外包法：将所有候选轨迹的采样点合并为一个点云（按权重过采样或保留权重），将问题退化为类似卡尔曼输出的处理方式——对合并后的加权点云计算 per-tile 概率（用核密度估计等方法）；
- C. 最大值法：P_nn(tile, t) = max_i p_i(tile, t)（保守策略，取各轨迹中最高的 tile 概率）。

建议选 A（加权平均法），理由：保持概率语义（权重之和为 1），计算直观，与 P_kalman 计算管线复用。

**四、P_final 中概率 p 的取值**

交底书定义 p = max_{t in [0,T]} P_final(tile, t)，即取预测时间窗口内各时刻概率的最大值。这意味着系统倾向于保守预加载（只要在未来任一时刻该 tile 可能被看到，就纳入考虑），符合预加载的宁可多加载不可漏掉原则。该设计合理。

待发明人确认后定稿。

### 7.1.1-Q4 优先级公式是否参考了特定文献

【答复草稿】

经检索公开文献和行业规范，该优先级公式的整体形式（概率加权画质改善 / 代价项加权和）未见于已知的标准文献或公开专利。分项分析如下：

**1. 分子部分 (p * DeltaQ)：**
- 概率 p 来自多模型轨迹预测融合，属于本发明的独创设计；
- DeltaQ（画质改善）的概念可类比于 3D Tiles 规范中用于 LOD 选择的 Screen Space Error (SSE) 计算思想（geometricError 映射到屏幕像素误差，参考 3D Tiles 1.1 Section C.2），但本发明的 DeltaQ 公式（tile.geometricError * tile.screenProjectionArea / tile.currentLODError）是自定义拓展，引入了 screenProjectionArea 和 currentLODError 两个非标准字段。

**2. 分母部分 (alpha*N + beta*C + epsilon)：**
- 将网络占用 N 和缓存压力 C 的线性加权作为加载代价，是资源约束下调度优化的常见建模手段，广泛见于自适应流媒体调度（如 MPEG-DASH 的 ABR 算法中带宽-缓冲联合优化）和边缘计算中的内容预取文献；
- 但 alpha + beta = 1.0 的二因子动态权重设计（随网络带宽调整）是本发明的具体实现选择。

**3. 整体公式：**
- 分子为预期收益（概率 * 画质改善），分母为代价，形式为 cost-benefit ratio，在调度优化领域（如计算卸载、缓存替换策略）中是常见范式；
- 但将轨迹预测概率、几何误差视点自适应、网络/缓存代价三者统一为单一优先级分数的具体公式（含 alpha/beta 动态调节），在 3D GIS / 空间数据加载领域未见完全相同文献。

结论：该公式的各组成部分（概率预测、SSE 类比、代价线性加权）分别有公开技术渊源，但整体公式组合及其在 3D 空间数据预加载中的具体应用场景属于本发明的独创设计。

【建议】在交底书中增加以下表述：「本发明的优先级计算公式为自定义的 cost-benefit 调度评分函数，其分子表征瓦片加载的预期视觉收益（由预测命中概率与 LOD 改善量共同决定），分母表征加载的资源代价（由网络带宽压力与缓存压力加权求和），整体构成单位代价下的预期收益指标，用于指导预加载优先级排序。该公式属于原创设计，未直接引用单一文献。」

### 7.1.1-Q6 DeltaQ 公式中各字段的精确计算方式

【答复草稿】

交底书记载 DeltaQ = tile.geometricError * tile.screenProjectionArea / tile.currentLODError，并标注待补充。以下基于公开规范和图形学常识给出各字段的精确计算建议。

**一、tile.geometricError**

该字段是 3D Tiles 规范（1.0 Section 7.2.4, 1.1 Section 7.2.5）定义的标准瓦片属性，单位为米，语义为「当该瓦片被渲染时，其几何表示与真实几何之间的最大误差（以米为单位）」。
- 来源：从 tileset.json 中直接读取每个 tile 的 geometricError 字段；
- 用法：这是标准字段，无需自定义计算。
- 注意：3D Tiles 规范中 geometricError 的常规用途是屏幕空间误差（SSE）判定：SSE = geometricError * screenHeight / (2 * distance * tan(fovY/2))。若 SSE 大于阈值（如 16 像素），则瓦片需细化为更高 LOD。本发明的 DeltaQ 并未直接复用此标准 SSE 公式，而是使用了自定义的 screenProjectionArea 和 currentLODError。

**二、tile.screenProjectionArea（待发明人确认）**

该字段在 3D Tiles 规范和 CesiumJS 源码中均非标准字段。以下给出三种自洽的计算方案。

【建议方案-待发明人确认】选A
- A. 包围体投影面积法：将 tile 的 boundingVolume（3D Tiles 支持 box/region/sphere 三种类型）投影到当前屏幕空间，计算其 2D 投影多边形的面积（单位为平方像素）。具体步骤：

### 7.1.2-Q5 三个调整因子的组合优先级与叠加方式

【答复草稿】

交底书原文分别给出了三个调整因子的独立公式，但未说明三者之间的组合关系。原文的三个公式分别为：

- 雾化：SSE_adjusted = SSE_base × [1.0 - exp(-(distance × density)^2)]
- 高度：SSE_threshold_adjusted = SSE_base × (1 + camera_height / scene_height_range)

【建议方案 A-待发明人确认：乘法叠加，顺序无关】

最终 SSE 阈值 = SSE_base × F_fog × F_height × F_horizon

其中：
- F_fog = 1.0 - exp(-(distance × density)^2)，取值范围 (0, 1)，远景瓦片被压缩
- F_height = 1 + camera_height / scene_height_range，取值 >= 1，高空时放宽阈值
- F_horizon = 1.5（地平线附近瓦片）or 1.0（其他瓦片），地平线附近额外放宽

三个因子为独立乘法因子，交换律保证叠加顺序不影响结果。最终 SSE_threshold_final 用于与每个瓦片自身的 SSE（由 geometricError 经透视投影计算得出）比较：若瓦片 SSE > SSE_threshold_final，则该瓦片需要细化（refine），加载更高精度的子瓦片。

该方案的优点：实现简洁、因子语义独立、与原文各公式的独立定义在逻辑上自洽。

【建议方案 B-待发明人确认：串行级联，顺序敏感】

SSE_threshold_1 = SSE_base × F_fog（雾化先行，产生 SSE_adjusted）
SSE_threshold_2 = SSE_threshold_1 × F_height（高度修正，产生 SSE_threshold_adjusted）
SSE_threshold_final = SSE_threshold_2 × F_horizon（地平线最终修正）

该方案下顺序有先后，暗示各因子的设计优先级不同。但需在交底书中明确解释为何选择此顺序（如：雾化先模拟大气衰减的物理直觉，高度再根据观测距离修正，地平线最后做特殊区域处理）。

【建议方案 C-待发明人确认：条件触发，非全量叠加】

不同调整因子在不同条件下选择性生效，而非三个因子总是同时作用：
- 雾化因子：始终生效（逐瓦片）
- 高度因子：仅当 camera_height > scene_height_range（即相机高于场景最高点）时生效，否则 F_height = 1
- 地平线因子：仅当夹角 < 5° 时生效，否则 F_horizon = 1

此方案更贴近各因子的设计意图（高空俯视才触发高度调整，地平线附近才触发地平线调整），且避免了非必要场景下的过度调整。该方案在乘法叠加框架下自然成立（非触发因子取 1），与方案 A 兼容。

**关于最终决策值的补充说明**

无论采用上述哪种组合方式，最终用于瓦片细化判定的值是经过所有调整因子作用后的 SSE_threshold_final（即综合 SSE 阈值）。判定逻辑为：

对于每个待判定的瓦片，计算其自身 SSE（= geometricError / distance × screenHeight / (2 × tan(fov/2))，此为标准透视投影 SSE 公式，见 3D Tiles 规范与 CesiumJS 实现），与 SSE_threshold_final 比较：
- 若 瓦片 SSE > SSE_threshold_final → 瓦片需要细化（refine），加载子瓦片
- 若 瓦片 SSE <= SSE_threshold_final → 瓦片保持当前精度，不再细化

这一判定流程与 3D Tiles 规范中的 Refinement 判定一致，仅将固定阈值替换为动态计算的综合阈值。

**建议补充：公式链（以方案 A+C 为例）**

SSE_threshold_final = SSE_base × F_fog(distance, density) × F_height(camera_height) × F_horizon(elevation_angle)

其中：
- SSE_base = maximumScreenSpaceError（如 16 像素）
- F_fog = 1.0 - exp(-(distance × density)^2)，density = 0.005 × (tile_count / view_distance)
- F_height = 1 + max(0, camera_height / scene_height_range)（非负保护）
- F_horizon = 1.5 if |elevation_angle| < 5° else 1.0

### 7.1.3-Q3 跳级判定公式与 SSE 策略的关系

【答复草稿】

**可直接确定的内容**

根据 3D Tiles 1.0/1.1 规范（Cesium GS, 3D Tiles Specification），SSE（Screen Space Error）是决定瓦片是否需要细化的标准机制，其计算公式为：

SSE = (geometricError × screenHeight) / (distance × 2 × tan(fov / 2))

当 SSE 大于 maxScreenSpaceError（通常取 16 像素）时，当前瓦片需要被其子级替换以获得更高精度的内容。SSE 回答的是「是否需要加载更高 LOD」这个二元问题，但 SSE 本身不提供「跳过中间层级」的决策逻辑——标准 3D Tiles 的 HLOD 细化策略是逐级替换（replace refinement）或累加（additive refinement），不会跳级。

本申请交底书提出的跳级判定公式：

tile.__error < ancestor.__error / 16 && depth > ancestor.depth + 1

是一个独立于 SSE 的新增判定条件：它不取代 SSE 的「是否需要细化」判断，而是在 SSE 已经判定「需要细化」之后，进一步回答「是否可以直接跳到当前候选瓦片，而跳过中间的若干层级」。换句话说，跳级公式解决的是 SSE 无法解决的「加载路径优化」问题，两者的分工如下：

- SSE：决定是否触发 LOD 细化（「要不要换」）；
- 跳级公式：在触发细化后，决定加载路径是否可以直接跨越中间层级（「怎么换」）。

因此，两者在逻辑上是先后关系（先 SSE 后跳级公式），而非对等的 OR/AND 关系。

交底书图 2 说明中的表述「但实际根据屏幕投影计算满足条件时可直接从 L0 跳到 L3」，其中「根据屏幕投影计算满足条件」所指的即为 SSE 判断——先由 SSE 判定当前视角下 L0 需要细化，再由跳级公式判定可以直接跳到 L3 加载，而不经过 L1、L2。这与上述「先后顺序」的解释完全一致。

**建议方案-待发明人确认**

关于 SSE 策略与跳级公式策略的确切执行顺序及保护重点，交底书未明确说明。以下提供三个技术自洽的可选方案，供发明人确认或选择：选A

【建议方案 A】SSE 前置 + 跳级公式后置（顺序结构）
- 流程：遍历瓦片树 → 对当前瓦片计算 SSE → 若 SSE ≤ 阈值，保持当前瓦片，不细化 → 若 SSE ＞ 阈值，进入细化流程 → 在细化流程中，对候选子瓦片执行跳级公式判定 → 若公式满足（tile.__error ＜ ancestor.__error / 16 且 depth ＞ ancestor.depth + 1），则跳过中间层级，直接加载该瓦片 → 否则走标准逐级细化路径。
- 逻辑：SSE 是跳级的前置条件（门控），只有 SSE 判定「需要细化」时才进入跳级判定；若 SSE 判定不需要细化，跳级公式根本不会执行。跳级公式仅在细化路径上选择「跳级」还是「逐级」。
- 技术特征：两套判定是串联顺序关系（先 SSE 后公式），不是 OR/AND 布尔逻辑关系。

【建议方案 B】SSE 与跳级公式联合判定（AND 关系）
- 流程：同时评估当前瓦片是否满足 SSE 细化条件 AND 当前候选子瓦片是否满足跳级公式条件，两者同时成立则触发跳级加载。
- 技术特征：两者为 AND 关系——必须 SSE 判定需要细化且跳级公式判定可跳级，才执行跳级；任一条件不满足则不跳级（可能退化为 SSE 驱动的标准逐级细化或其他回退策略）。
- 与前文的衔接：该方案与图 2 说明中「根据屏幕投影计算满足条件时可直接从 L0 跳到 L3」的表述兼容，但在专利撰写时需明确强调 AND 关系而非顺序关系。

【建议方案 C】跳级公式作为独立判定，可独立触发跳级
- 流程：跳级公式独立于 SSE 运行——无论 SSE 是否判定需要细化，只要跳级公式条件满足（tile.__error ＜ ancestor.__error / 16 且 depth ＞ ancestor.depth + 1），即可跳过中间层级直接加载目标瓦片。
- 技术特征：跳级公式本身即包含了几何误差的相对比较，隐式表达了「目标瓦片在当前视距下已经足够精细」的判断，因此可以不依赖 SSE 而独立运作。
- 注意：该方案与常规 3D Tiles 实现（总是以 SSE 驱动细化）差异较大，需发明人确认本申请的实际实现路径是否如此。

### 7.2-Q6 预加载数据是否包含所有 LOD 层级及 K 的取值规则

【答复草稿】

**（一）预加载数据是否包含所有 LOD 层级**

交底书步骤 3-4 仅表述"计算瓦片预加载优先级，按 Priority 排序"与"根据优先级队列主动预加载瓦片到缓存池"，未明确预加载内容包含的 LOD 层级范围。在 3D Tiles 规范（CesiumGS/3d-tiles）中，瓦片树中的每个瓦片节点对应于一个确定的 LOD 层级（由其在树中的深度以及 geometricError 决定），不存在单个"瓦片节点"同时包含 L0~L3 所有层级数据的概念。因此，"预加载的瓦片数据"应理解为：被选中预加载的瓦片节点，其数据内容为该节点自身对应的单一 LOD 层级的数据（几何、纹理、属性等），而非该瓦片节点的全部祖先或子孙层级数据。

在此基础上，预加载策略涉及两个层面的决策：选A

（a）预加载目标层级的选择：轨迹预测模块输出未来视点的概率分布后，系统依据预测视点计算每个候选瓦片的 SSE（Screen Space Error），判定其在预测视点下应使用哪个 LOD 层级（目标层级）。预加载时应加载该瓦片的目标层级数据。

（b）是否连带加载关联层级：即目标层级确定后，是否同时预加载其父级（更粗糙）或子级（更精细）数据作为预测兜底。

【建议方案 A — 精确加载】（推荐）：仅预加载预测目标层级的单一层级数据。优势：带宽利用率最高，与"基于预测的主动加载"的发明目标一致；劣势：若预测偏差较大，需回退加载。

【建议方案 B — 安全裕度加载】：预加载预测目标层级数据，同时附带加载该层级上一级（父级，更粗糙）数据。优势：即使预测略有偏差，仍可降级渲染父级瓦片，用户体验更平滑；劣势：带宽开销增大。

【建议方案 C — 预测概率加权加载】：根据预测模块输出的概率分布，选择概率最高的前 N 个层级组合进行预加载（如目标层级概率 0.7 时仅加载该层，概率 0.5 时同时加载 ±1 层）。优势：自适应；劣势：实现复杂度较高。

**（二）K 的取值规则**

交底书 7.1.1 节仅提及"选择前 K 个瓦片进行预加载"，K 的具体取值规则未载明。K 值的确定需与 7.1.1-Q8 中"候选集范围"保持一致（K 表示从候选集中选取前 K 个）。选A

【建议方案 A — 固定值】：K 为预设常数（如 K=20），基于实验或经验确定，适用于目标部署环境的典型网络与硬件条件。

【建议方案 B — 动态自适应】：K 根据当前可用带宽、缓存池剩余容量、预测置信度等运行时参数动态调整。例如：K = min(K_max, floor(B_avail / B_per_tile))，其中 B_avail 为可用带宽预算，B_per_tile 为单瓦片平均数据量。

【建议方案 C — 容量驱动】：K 由缓存池当前空闲槽位数决定，即 K = max(0, C_total - C_occupied)，在不超过缓存容量的前提下最大化预加载数量。

**（三）每个瓦片是否默认预加载全部层级数据**

基于上文（一）的分析：每个被选中预加载的瓦片节点仅加载其自身对应层级的单一层级数据，不默认预加载其全部层级数据。否则，"预测驱动的精准加载"的创新点将失去意义——若每次预加载都加载全部层级，则等同于全量预取，与现有技术的全量加载无实质性区别。

### 7.2-Q8 优先级计算范围与跨层级排序方式

【答复草稿】

**（一）优先级计算的范围**

【建议方案 A — 预测视锥体范围】（推荐）：以轨迹预测模块输出的未来 N 帧（或未来 T 秒）的预测视锥体所覆盖的瓦片集合为候选集。具体而言，对预测概率分布中概率超过阈值 θ 的每个未来视点状态，计算其视锥体包围的瓦片集合，取并集作为候选集。这使候选集天然与预测结果对齐，且可通过调整 θ 和 N 控制规模。此方案与 3D Tiles 规范中基于视锥体的可见性判定逻辑自洽。

【建议方案 B — 当前视锥体+预测扩展范围】：候选集 = 当前视锥体内的瓦片 ∪ 预测模块判定未来可能进入视锥体的瓦片。优势：兼顾当前渲染需求与未来预加载需求；劣势：候选集规模受当前视锥体影响，可能导致预加载"前瞻性"不足。

【建议方案 C — 全量全局范围】：对所有层级的所有已注册瓦片计算优先级。优势：保证全局最优排序；劣势：瓦片数量可能达数万至数十万，逐帧全量计算 Priority 的计算开销可能超过 GPU 帧时间预算，实用性存疑。

**（二）每个瓦片的优先级是单层级优先级还是综合优先级**

交底书 7.1.1 节给出的 Priority 公式（与 7.1.1-Q8 关联）所描述的计算对象为单一瓦片节点。在 3D Tiles 中，每个瓦片节点对应一个确定的 LOD 层级，因此 Priority 应理解为**单个瓦片节点在其所在层级上的预加载优先级**，而非跨层级的综合优先级。

【建议方案 B — 分层排序+配额分配】：按 LOD 层级分层，每层内部独立排序，再按预设配额（如 L0 占 30%、L1 占 30%、L2 占 25%、L3 占 15%）从各层选取。优势：保证各层级都有瓦片被预加载，避免层级间资源挤占；劣势：配额分配需调参，灵活性下降。

### 7.2-Q9 跳级判定后的具体加载行为与不跳级时的行为

【答复草稿】

**（一）跳级后的加载行为**

交底书步骤 6 表述为"通过跳级判定条件决定是否跳过中间层级"，图 4 说明中空域优化层负责"对当前视锥体内数据进行 LOD 调度和内存优化"。此处的"跳级"是相对于传统 3D Tiles 逐级细化（从 L0→L1→L2→L3 依次加载）的"非线性"跳转。

在 3D Tiles 规范中，瓦片树的细化方式有两种：REPLACE（子级替换父级）和 ADD（子级叠加到父级之上）。跳级行为需与该细化模式协调。选B

【建议方案 A — 直接跳至目标层级】：若跳级判定条件满足（例如：当前已加载层级与 SSE 计算所得目标层级之间的层级差超过预设跳级阈值 Δ），则跳过所有中间层级，直接发起目标层级瓦片数据的网络请求并加载至缓存。优势：最少网络请求，延迟最低；劣势：若中间层级数据量大、网络慢，可能出现短暂空白。适用场景：REPLACE 细化模式下的瓦片集。

【建议方案 B — 保留根节点+跳至目标层级】：始终保留 L0（根层级/最粗糙层级）数据在缓存中作为兜底，在此基础上跳过中间层级直接加载目标层级。优势：跳级过程中 L0 持续提供最低保真度渲染，用户无空白感知；劣势：L0 始终占用缓存空间。适用场景：ADD 细化模式或追求渲染连续性的场景。

【建议方案 C — 分级跳级】：根据层级差的大小分级处理。层级差 ≤ 2 时正常逐级加载；层级差 > 2 时跳至目标层级。优势：在"小幅跨级"和"大幅跨级"间取得平衡；劣势：判定逻辑略复杂。

**（二）不跳级时的加载行为**

当跳级判定条件不满足时，系统应遵循正常的逐级细化流程：从当前已加载层级开始，依次加载下一层级，直至达到目标层级。即：若当前已加载 L0，目标层级为 L3，且不满足跳级条件，则依次加载 L1、L2、L3 的对应瓦片数据。这与 3D Tiles 规范中的标准细化流程一致（CesiumJS 中通过 TileTraversal 算法逐级遍历瓦片树并加载满足 SSE 阈值的子瓦片）。选A

【建议方案 A — 严格逐级】：加载当前层级到目标层级之间的每一个中间层级，一步不缺。

【建议方案 B — 按需逐级】：加载下一个中间层级后重新计算 SSE，若目标层级已变化则按新目标层级继续，而非锁定初始目标层级。优势：响应动态视点变化；劣势：逻辑复杂。

待发明人确认上述建议方案的选择后定稿。

【决策点】
- 【7.2-Q9-决策1】跳级行为：选择方案 A（直接跳至目标层级）、方案 B（保留 L0+跳至目标层级）还是方案 C（分级跳级）？需说明与瓦片集细化模式（REPLACE/ADD）的关系。
- 【7.2-Q9-决策2】跳级阈值 Δ：跳级判定条件中的层级差阈值取值是多少（如 Δ=2 表示当前层级与目标层级差 ≥ 2 时触发跳级）？Δ=2
- 【7.2-Q9-决策3】不跳级时的行为：选择方案 A（严格逐级加载所有中间层级）还是方案 B（按需逐级，动态重算 SSE）？

### 7.2-Q10 步骤 8（onAfterRender 释放）与步骤 9（LRU 卸载）的差异

【答复草稿】

交底书步骤 8 和步骤 9 描述了两种不同粒度的数据释放操作，需严格区分：

**（一）步骤 8（onAfterRender 钩子释放 CPU 侧数据）与步骤 9（LRU 卸载完整瓦片数据）的关系**

根据 7.1.4 节原文："用后即卸在 onAfterRender 中释放 CPU 侧 attribute.array、mipmaps、image，仅保留 GPU 显存副本"。这表明步骤 8 是**部分释放**：瓦片首次渲染完成后，立即释放 CPU 内存中的顶点数组（attribute.array）、贴图数据（mipmaps）、图像数据（image），但保留 GPU 显存中的对应副本（WebGL Buffer/Texture 对象），以便后续帧直接使用 GPU 端数据进行渲染，无需重复上传。

步骤 9 的"卸载完整瓦片数据"则发生在瓦片离开视锥体或缓存池达到容量上限时，是**完全释放**：不仅移除缓存池中的瓦片引用，还应释放 GPU 侧显存资源。

**（二）"完整"的含义** 选A

【建议方案 A — CPU+GPU 双向删除】（推荐）："完整"指同时删除 CPU 侧和 GPU 侧的瓦片数据。具体操作包括：（1）从 TileCache 缓存池中移除该瓦片条目；（2）调用 WebGL API 显式释放 GPU 资源（gl.deleteBuffer 删除顶点缓冲、gl.deleteTexture 删除纹理对象、gl.deleteProgram 删除着色器程序等）；（3）解除 JavaScript 对象引用，使 JS 垃圾回收器可回收 CPU 内存中的管理对象（如 Tile 实例本身、元数据对象等）。依据：WebGL 规范明确要求显式调用 delete* 方法释放 GPU 资源，JavaScript GC 不会自动回收 GPU 显存（GPU 资源由浏览器 WebGL 实现管理，独立于 JS 堆）。

【建议方案 B — 仅从缓存池移除引用】："完整"仅指从 TileCache 缓存池中移除该瓦片的管理条目（包括元数据、引用句柄），GPU 资源的释放依赖 JavaScript 垃圾回收机制。不推荐：WebGL 资源（Buffer、Texture）并非 GC 自动管理，仅移除 JS 引用而不显式 delete 可能导致 GPU 显存泄漏。

**（三）LRU 卸载操作包含的具体数据**

【建议方案 — 基于方案 A 的具体数据清单】：
- CPU 侧：瓦片元数据（tile transform、bounding volume、geometricError 等）、几何数据（若步骤 8 未释放或有新瓦片未渲染）、纹理数据（若步骤 8 未释放或有新瓦片未渲染）
- GPU 侧：顶点缓冲对象（VBO，对应 gl.deleteBuffer）、索引缓冲对象（IBO，对应 gl.deleteBuffer）、纹理对象（对应 gl.deleteTexture）、帧缓冲对象（如有，对应 gl.deleteFramebuffer）
- 缓存管理数据：TileCache 中的瓦片条目（优先级、访问时间戳、引用计数等）

**（四）GPU 侧数据的释放方式**

在 WebGL/Three.js 技术背景下，GPU 资源的释放必须通过 WebGL API 显式调用，而非依赖 JavaScript 垃圾回收：选A

【建议方案 A — WebGL 显式删除】（推荐）：通过 gl.deleteBuffer() 删除 VBO/IBO，通过 gl.deleteTexture() 删除纹理对象。在 Three.js 中，可通过调用 BufferGeometry.dispose() 和 Texture.dispose()（内部封装了上述 WebGL 调用）实现。依据：WebGL 1.0/2.0 规范，GPU 资源由浏览器进程中的 GPU 进程管理，JavaScript GC 仅管理 JS 堆中的包装对象，不会触发底层 GPU 内存回收。MDN WebGL 教程亦明确指出需显式调用 delete* 方法。

【建议方案 B — Three.js dispose+remove】：调用 Three.js 的 renderer.dispose() 或手动遍历场景中的 geometry/material/texture 并调用其 dispose() 方法，然后从场景中 remove 相关对象并解除引用。本质与方案 A 相同，均为显式 WebGL 调用，仅是 API 封装层级不同。

【建议方案 C — 依赖 JS 垃圾回收】（不推荐）：仅解除 JS 引用，依赖 GC 触发 WebGL 资源回收。依据 MDN/WebGL 最佳实践，此方式不可靠，可能导致 GPU 显存持续增长直至页面崩溃。

待发明人确认上述建议方案的选择后定稿。

【决策点】
- 【7.2-Q10-决策1】"完整"的定义：选择方案 A（CPU+GPU 双向删除）还是方案 B（仅从缓存池移除引用）？若选 A，是否认可步骤 8（onAfterRender CPU 释放）与步骤 9（LRU GPU+CPU 完整卸载）的两阶段释放模型？
- 【7.2-Q10-决策2】GPU 释放方式：选择方案 A（WebGL 显式 deleteBuffer/deleteTexture）、方案 B（Three.js dispose）还是其他？方案 A 与 B 本质等价，选用取决于系统是基于原生 WebGL 还是 Three.js 封装。
- 【7.2-Q10-决策3】LRU 卸载的触发条件：除"瓦片离开视锥体"和"缓存达到上限"外，是否还有其他触发条件（如瓦片优先级低于阈值、预测概率低于阈值）？确认
- 【7.2-Q10-决策4】LRU 卸载时，若瓦片数据尚未完成步骤 8 的 onAfterRender（即尚未首次渲染），卸载行为是否相同？即是否仍需清理 GPU 资源（此时 GPU 资源可能尚未创建）？检查有就释放，没有则不需要。
